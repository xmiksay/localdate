# letsgo.sc-l.eu: example deployment

An example deployment of localdate at <https://letsgo.sc-l.eu> on the `k8s-new` cluster. It is a
kustomization in namespace `letsgo`. Unlike [`deploy/k8s.yml`](../k8s.yml), it runs no Postgres and
has no volumes: the database is the shared Postgres behind `services`, and photos go to a Garage
bucket. General operations (updates, rollback, backups, provider details) are in
[docs/deployment.md](../../docs/deployment.md). This file covers only what differs here.

| Object | What |
|---|---|
| `Namespace letsgo` | everything below |
| `ConfigMap letsgo` | `BIND_ADDR`, `RUST_LOG`, `CLEANUP_INTERVAL_SECS`, `PHOTO_STORAGE=s3`, `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `TRUST_PROXY_HEADERS=true`, `APP_BASE_URL`, `EMAIL_FROM`, `VAPID_SUBJECT` |
| `Secret letsgo` (by hand) | `DATABASE_URL`, `JWT_SECRET`, optional integrations ([secret.example.yaml](secret.example.yaml)) |
| `Secret letsgo-s3` (by hand) | copy of `services/letsgo-s3` from the Garage repo: `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, … |
| `Deployment localdate-api` | 1 replica, `Recreate`, read-only root FS, no volumes |
| `Service localdate-api` + `Ingress letsgo` | Traefik, cert-manager `letsencrypt-prod`, TLS Secret `letsgo-sc-l-eu-tls` |

> **Requires an image with S3 photo storage (#21).** Older images ignore `PHOTO_STORAGE` and write
> photos to `/data/photos`, which is on the read-only root FS. The pod still starts, but every photo
> upload fails. Deploy only once `ghcr.io/xmiksay/localdate:master` contains #21.

No NetworkPolicy: the cluster's CNI is flannel, which does not enforce them, and no other namespace
defines any.

## 1. Postgres role and database

Postgres runs on the `db` VPS (172.19.9.2), outside the cluster. The `services/postgres` Service
points at PgBouncer, and `services/postgres-direct` points at Postgres itself. `pg_hba` is generated by
Ansible and admits each database's owner only. A role and database created by hand with SQL are
therefore **rejected** until Ansible knows them, and Ansible resets every listed role's password to
its vault value. Create them through `personal/ansible`:

```sh
cd ~/projects/personal/ansible
# inventory/group_vars/pg/main.yml: add `letsgo` to pg_roles, and to pg_databases:
#   - {name: letsgo, owner: letsgo, backup: true}   # profiles, messages: personal data
# secrets/dbhosts.vault.yml: add pg_passwords.letsgo, URL-safe because it goes into DATABASE_URL:
openssl rand -hex 24
make dbhosts                       # creates role + database, regenerates pg_hba
make pg-password ROLE=letsgo       # prints the password, for step 3
```

The SQL this amounts to, for reference or for checking in pgAdmin (<https://pg.mmik.cz>) as `postgres`.
No `CREATEDB` is needed: test databases are only created locally.

```sql
CREATE ROLE letsgo LOGIN PASSWORD '<openssl rand -hex 24>';
CREATE DATABASE letsgo OWNER letsgo;
```

**Use `postgres-direct`, not `postgres`.** PgBouncer runs `pool_mode = transaction`. In that mode
the WebSocket bridge's `LISTEN` (`ws/bridge.rs`) never receives notifications, so live push would
break silently. Cluster clients reach Postgres over TLS only (`hostssl`), hence `sslmode=require`.
Direct connections bypass PgBouncer's per-database cap: each replica holds its SeaORM pool (sqlx
default: 10) plus one listener against `max_connections=100`.

## 2. Photo bucket

```sh
cd ~/projects/personal/garage && make bucket APP=letsgo     # bucket + key + Secret services/letsgo-s3
kubectl create namespace letsgo --dry-run=client -o yaml | kubectl apply -f -
kubectl -n services get secret letsgo-s3 -o json \
  | jq '{apiVersion, kind, type, data, metadata: {name: .metadata.name, namespace: "letsgo"}}' \
  | kubectl apply -f -
```

No CORS is needed: browsers never talk to Garage, the API streams photos under `/media`. Consider
adding the bucket to `garage_buckets` with `backup: true` in `personal/ansible` (nightly NAS copy).
Back it up together with the database: a photo row without its object renders a broken image.

## 3. Secret `letsgo`

```sh
PG_PASSWORD='<from make pg-password ROLE=letsgo>'
kubectl -n letsgo create secret generic letsgo \
  --from-literal=DATABASE_URL="postgres://letsgo:${PG_PASSWORD}@postgres-direct.services.svc:5432/letsgo?sslmode=require" \
  --from-literal=JWT_SECRET="$(openssl rand -hex 32)"
unset PG_PASSWORD
```

Add an optional integration later by patching the Secret and restarting. Env is read at start only:

```sh
kubectl -n letsgo patch secret letsgo --type merge \
  -p '{"stringData":{"GOOGLE_CLIENT_ID":"<id>.apps.googleusercontent.com","GOOGLE_CLIENT_SECRET":"<secret>"}}'
kubectl -n letsgo rollout restart deployment/localdate-api
```

Keys: `SMTP_URL`; `GOOGLE_CLIENT_ID` + `GOOGLE_CLIENT_SECRET`; `TELEGRAM_CLIENT_ID` +
`TELEGRAM_CLIENT_SECRET`; `TELEGRAM_BOT_TOKEN`; `FACEBOOK_APP_ID` + `FACEBOOK_APP_SECRET`;
`VAPID_PUBLIC_KEY` + `VAPID_PRIVATE_KEY`. Pairs are both-or-neither. The API refuses to start with half
of one, so the restarted pod will crash-loop while the old one keeps serving until you fix it.

## 4. Provider setup

Follow docs/deployment.md, with `letsgo.sc-l.eu` in place of `localdate.mmik.cz`:

- [Google](../../docs/deployment.md#sign-in-with-google-optional): authorized redirect URI
  `https://letsgo.sc-l.eu/api/auth/oauth/google/callback`, authorized domain `sc-l.eu`.
- [Telegram](../../docs/deployment.md#telegram-login-and-reset-messages-optional): BotFather → Login
  Widget Allowed URLs `https://letsgo.sc-l.eu` and `https://letsgo.sc-l.eu/api/auth/oauth/telegram/callback`.
  The bot token must belong to the login bot.
- [Facebook](../../docs/deployment.md#facebook-login-optional): Valid OAuth Redirect URI
  `https://letsgo.sc-l.eu/api/auth/oauth/facebook/callback`, App Domain `letsgo.sc-l.eu`. A Privacy
  Policy URL and a Data deletion instructions URL are required before the app can go Live.
- [Email](../../docs/deployment.md#email-magic-link): `SMTP_URL` in the Secret. Set SPF/DKIM for
  `letsgo.sc-l.eu` (or change `EMAIL_FROM` in configmap.yaml to a domain that has them).
- [Web Push](../../docs/deployment.md#web-push-optional): `make vapid-keys`, both keys into the Secret.

## 5. Deploy

```sh
kubectl config current-context        # must be k8s-new
make deploy-letsgo-diff               # kubectl diff -k deploy/letsgo
make deploy-letsgo                    # kubectl apply -k deploy/letsgo
kubectl -n letsgo rollout status deployment/localdate-api
kubectl -n letsgo get certificate letsgo-sc-l-eu-tls   # READY=True after the HTTP-01 challenge
curl -fsS https://letsgo.sc-l.eu/api/health
```

First admin, after the user has registered and the rollout has finished (the CLI refuses to run
while migrations are pending):

```sh
kubectl -n letsgo exec deploy/localdate-api -- localdate-api admin grant <username>
```

New `master` build: `kubectl -n letsgo rollout restart deployment/localdate-api`. ConfigMap
changes: `make deploy-letsgo`, then the same restart.

## Client IP

`TRUST_PROXY_HEADERS=true` makes the login/register rate limiter key on the **first**
`X-Forwarded-For` entry (`rate_limit::client_ip`). That is only safe when the proxy replaces the
header instead of appending to a client-supplied one. Checked on `k8s-new` (read-only, Traefik
v3.7 DaemonSet in namespace `traefik`):

- Traefik runs with `hostNetwork: true` on k8s-master, which holds the public IP 37.205.11.119. No
  load balancer or SNAT sits in front, so Traefik sees the real client address.
- No `--entryPoints.*.forwardedHeaders.trustedIPs` or `.insecure` is set, so no source is trusted.
  Traefik then **deletes** incoming `X-Forwarded-*` headers before proxying and appends the peer
  address. The first entry is the real client.

The flag is therefore safe. It stops being safe if either changes. Check with
`kubectl -n traefik get ds traefik -o yaml | grep -i forwarded`. With `forwardedHeaders.insecure`, or
`trustedIPs` covering arbitrary clients, the first entry is client-chosen and anyone can dodge the
limiter. In that case set `TRUST_PROXY_HEADERS=false`.
